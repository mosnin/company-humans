# Security

The health endpoint returns only service status and revision. Phase 01 now has a Clerk identity boundary and a restricted tenant organization route. Live Clerk configuration, complete server authorization, service credentials, and additional tenant policies remain. The source Convex Auth proxy was intentionally excluded.

The Phase 00 envelope library validates versioned event and audit fields and can sign and verify them with a caller supplied 32 byte or longer key. No production signing key exists in this repository. API authentication, key storage, rotation, replay/idempotency enforcement, and audit persistence remain unimplemented.

Phase 01 has begun with a Clerk webhook and canonical user table. The webhook refuses requests when its signing secret or database URL is absent and rejects failed signature verification before database mutation. The on-request resolver checks Clerk session identity and then loads or creates a canonical active user. Live Clerk delivery and sign-in remain unverified because no Clerk application keys or webhook configuration are available in this workspace.

Organization creation and owner membership are atomic. Migration `0004_tenant_rls.sql` enables RLS on organizations and memberships and grants restricted reads to `company_human_app`. The `/api/organizations` route resolves the Clerk session to a canonical user and performs its query through `DATABASE_RUNTIME_URL`, which must use a separate login role granted `company_human_app`. The database helper rejects a superuser, a BYPASSRLS role, or the table owner. A transaction local user context is set before the query and cleared on commit. Local integration tests exercise two tenants through a restricted login and deny cross tenant reads and writes.

The runtime login is a trusted server credential. PostgreSQL custom settings are writable by that login, so RLS does not defend against arbitrary SQL execution under that credential. Production must keep the connection server only, use parameterized queries, and prohibit client access to the database. The migration connection retains elevated permissions solely for migrations and narrow server operations such as Clerk sync and organization creation. A future authorization service must remove those privileged application paths before Phase 01 is verified. No live Clerk session or hosted isolation test has run.

The six initial roles have an explicit capability matrix. Finance does not inherit CRM or context access; Developer does not inherit payout or CRM access. Team managers can assign members only to their own active team and cannot promote another team manager. Team mutation helpers check the actor, organization, team, and target membership within one transaction. These helpers are internal and must receive actor identity from verified server authentication when exposed through an API.

Invitations store only SHA-256 hashes of 256 bit random tokens. Acceptance locks the invitation, requires a matching active canonical user's email, and consumes the token once. Owner and Admin may suspend, reactivate, or remove members within their organization, with Owner only authority over Admin. Owner membership cannot be suspended or removed through this route. Restricted RLS access context returns no membership for suspended or removed users. Removal ends team grants and revokes matching pending invitations. The API currently returns the invite token to the authenticated Admin for manual delivery; email delivery and live Clerk session revocation are not implemented. Product adapter offboarding begins in later phases.
