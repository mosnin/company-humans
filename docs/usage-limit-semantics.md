# Product usage limit configuration

Canonical documents 03/06 and CH-18 require member capabilities and finite usage limits. The existing V1/V2 adapter limit field is only a string-to-number record: it does not specify units, reset windows or revision acknowledgement. It cannot by itself prove the required budget/enforcement behavior. No adapter interpretation is invented here.

The next configuration boundary stores a product-instance limit for a named catalog meter, at organization-default or explicit member scope. Each policy identifies the meter unit and a UTC calendar day, ISO week (Monday start) or calendar month. Quantity is a nonnegative exact decimal string with up to twelve integer and six fractional digits. Zero means stop; there is no unlimited sentinel. Changing quantity appends a revision with actor and audit. Organization and member caps are cumulative constraints; a larger member cap cannot enlarge an organization cap. They do not represent reserved allocation or remaining balance.

These are explicit implementation semantics for finite product limits, not a replacement for the full Phase 03 budget hierarchy. Team/capability budgets, commercial state, rolling windows if later required, thresholds, soft stops, usage aggregation, reservations/concurrency, outage enforcement, rate conversion, adapter application and acknowledgement remain unfinished. Products need a verified meter/unit/window mapping before any of these limits can authorize work. Unit changes require a distinct correctly registered meter; historical unit interpretation is immutable.

## Exact limit transport extension — 2026-09-21

Before implementing transport, documents 05/06 were rechecked. The existing numeric dictionary cannot acknowledge the saved semantics. Add a separately versioned usage-limit extension to V2 instead of changing existing V1/V2 methods in place. The extension applies one complete immutable limit revision to a verified external organization and, for member scope, its bound external member. Organization scope is aggregate across that organization's members, not a replicated per-member allowance. All applicable parent and member limits must eventually be enforced together.

Apply must be idempotent, reject stale revisions, preserve accumulated usage across quantity/revision changes, and keep existing member suspension unchanged. Readback must identify the exact canonical revision, provider target, hard-stop mode and preserved accounting. No automatic translation to the legacy numeric dictionary is allowed. Unsupported units/windows or absent provider enforcement must fail explicitly. A structurally valid receipt is a transport acknowledgement, not evidence of real provider behavior or permission to activate a member.

Compatibility: existing V1 organization/denial and V2 suspended bootstrap operations continue unchanged. Adoption requires each adapter to implement extension version 1, pass contract tests, and demonstrate actual aggregate/window/counter semantics against its provider. No date-based removal of legacy contracts is scheduled before those acceptance gates. Durable policy dispatch, complete snapshot/resolver fencing, all-limits readback, runtime usage enforcement and activation remain separate unfinished work.

The later version 1 product meter enforcement declaration pins a meter definition version, but this existing limit transport and its stored policy do not carry that version. It cannot be used to match a declaration to a provider readback. A separately versioned limit boundary and a central registration verifier must establish exact meter-version compatibility before readiness can change; current activation stays closed.
