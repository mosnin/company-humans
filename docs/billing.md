# Billing

Signed usage ingestion and authorized usage reads exist, but consolidated billing, valuation and spend enforcement are not active. Company Human must become the commercial authority for organization sponsored ecosystem usage, with measured variable cost and budget controls. Source Company OS Stripe plans were intentionally excluded. Merchant customer billing remains in the merchant product.

## Entitlement configuration status

Desired allow/deny/inherit settings are now versioned per product instance and optional member. They neither establish a commercial plan nor authorize spend. Versioned budget configuration and an advisory reported-consumption comparison exist; an authoritative spend decision, effective entitlement resolution and product-side enforcement remain unimplemented.

## Finite limit intent

Product-instance and member meter limits now have exact decimal, versioned configuration with explicit UTC calendar windows. Zero is a stop; unlimited values are rejected. This does not yet implement the budget engine, usage accumulation, parent/child evaluation, concurrency reservations, warnings, soft stops, billing or actual provider hard stops. The [limit semantics and adapter gap](usage-limit-semantics.md) must be resolved with verified meter/unit/window mappings before enabling spend.

The authenticated usage-limit mutation endpoint now persists this desired configuration. Its response explicitly reports providerEnforcementConfirmed=false. Saving does not evaluate usage or enforce a provider hard stop.

Organization and member usage-limit administration now exposes this configuration with exact quantities, UTC windows, immutable units and revision conflict handling. It displays parent organization caps separately and explicitly states enforcement is unconfirmed. It does not calculate remaining capacity or authorize unlimited usage when unconfigured.

### Usage ingestion storage (CH-20 preparation)

The signed usage contract and restricted transactional ingestion library now exist. Valid canonical meter/version/unit events are accepted; unknown or mismatched meters are retained in quarantine. Identical retries return the existing event; changed retries fail with an idempotency conflict. Original signed JSON is preserved even when numeric storage normalizes decimal formatting. The signed HTTP endpoint now uses an operator-configured credential registry (see integrations.md). No valuation, invoice or charge is produced. Source cost and customer-rate version remain explicit nullable provenance until real providers/pricing supply them.

### Scoped usage windows (CH-21 preparation)

Exact decimal usage aggregates now support half-open occurrence windows and organization, product, instance, team, member and reported capability breakdowns. Product, meter version and unit remain separate. Sum, maximum and deterministic last-value meters are supported; late reports appear on the next read. Existing organization and other non-capability totals continue to combine all capability values. Only accepted events count. This is a live read projection, not a durable billing snapshot or budget reservation. The authenticated usage API labels results permitted-usage: contributors see their authorized subset, managers their managed teams and finance/admin their authorized organization totals. No invoice, charge or live provider enforcement is claimed.

An exact `capabilityKey` filter is accepted only with the capability breakdown, so filtered responses retain their named key. A null capability row means the source event did not report one; it is not free usage.

Quarantined events can now be released after an exact product/meter/version/unit is registered. A budgets.manage-authorized action appends a release receipt; it never changes the source event. Aggregation includes the released event once. Historical valuation and billing snapshots remain unimplemented.

The CH-22 shared contract now describes separate organization, product, product-instance, operation-team, member, capability and meter policy scopes for a single exact product meter/version/unit and UTC day/week/month window. A pure resolver retains every applicable threshold and its own action, returns the earliest configured threshold without treating it as a spend decision, and rejects missing or mismatched team attribution. A separate pure evaluator compares complete, caller-supplied scope quantities with every threshold using exact decimals and canonical UTC periods. It requires an expected environment, aggregation mode and instant; missing coverage fails closed. This is a comparison, not a spending decision. Migration 0069 validates a named human usage team against assignment time; a null team and non-human attribution remain insufficient for team limits. Migration 0070 stores versioned, audited policy intent and supports disable/re-enable without deleting history. Its authenticated administration API reads the complete current set for one exact product meter; every response reports provider enforcement unconfirmed. Migration 0071 projects an optional signed capability key from the immutable event envelope. Older events retain unknown attribution as null; null must never be counted as zero capability usage by a future decision. The reported key is not proof that an operation was authorized for that capability. No capacity reservation, priced cross-product budget, or provider stop is implemented.

The dedicated Usage page reports the authenticated reader's permitted consumption by product/meter, with explicit production/test and inclusive UTC dates. It preserves exact numeric strings and labels total, peak and latest-value aggregation. It does not show a bill estimate or claim provider enforcement.

Migration 0072 adds a restricted, read-only budget snapshot diagnostic. It reads current policy and reported usage for each applicable scope and UTC window in one repeatable-read transaction, checks current catalog and member/team bindings, and fails when policy coverage or constrained attribution is incomplete. Its result always states `authorizesUsage=false` and `providerEnforcementConfirmed=false`. It neither reserves capacity nor proves a provider hard stop. No application endpoint calls this diagnostic yet; a dedicated restricted login must be configured before server use.

The V1 pre-cost reservation **contract** defines a source operation key independent of the transport retry key, exact prospective `sum` comparison (accepted/released usage plus outstanding reservations plus requested quantity), and append-only capacity transitions with late actual-usage reconciliation after settlement, release or expiry. It retains each policy action and always reports `authorizesUsage=false` and `providerEnforcementConfirmed=false`. At its initial contract checkpoint, this was pure code with no reservation table, transactional writer, approval flow or provider call. Migration 0075 adds inaccessible storage; the writer and provider call remain absent. The optional signed usage operation ID is signer-reported provenance; settlement cannot be trusted until a restricted transaction verifies the event, provider-operation binding and unique event-to-reservation reconciliation. `maximum` and `last` meters have no reservation semantics yet.

A signed usage event may now report an optional source operation ID, projected by migration 0074. This supports a future match to a reservation while preserving old events as unknown. The reported ID alone does not prove that a provider operation occurred, that its cost was authorized, or that a usage event should settle a reservation. A later restricted writer must verify the stored signed event and all tenant/product/instance/member/team/capability/meter/source bindings, then enforce unique event settlement and late reconciliation.

Migration 0075 stores only inaccessible reservation intent and ledger candidates. It neither holds spend capacity nor calculates a bill. An administrator fixture can insert a relationally matching event without a real signature, so stored settlement-shaped rows are not evidence of a real payment or provider operation. Multiple signed usage events per source operation can be represented after an initial settlement; no event may be reused in the ledger. Before any reader, writer, grant, policy or provider decision is added, Company Human must validate the complete V1 intent and current policies, verify team attribution and signed ingestion provenance, prove two-client ordering and atomic scope locking, and independently review the writable path.

A server-only read-only verifier can now authenticate the exact raw stored usage body before schema normalization against an operator-supplied active signing authority, then compare the signed event with its stored tenant, product, instance, human actor, member/team attribution, meter, quantity, source and timestamps. It requires a present source operation ID and exact registered sum meter. A quarantine release is observed as a database receipt, but that receipt is not independently authenticated by this verifier. Its result explicitly remains ineligible for settlement and does not authorize usage or provider action. The existing ingestion role still has direct INSERT, so raw `accepted` rows and aggregate totals cannot be treated as cryptographically verified. No reservation table grant or writer has been added.

The staged 0076 database signing-key registry and HMAC function have no runtime caller or EXECUTE grant. Current usage aggregation still reads accepted/released rows from the existing ingestion path; 0076 does not change commercial authority, reserve spend, value usage or create invoices. A later cutover must remove the direct ingestion INSERT only after the replacement function and source-key lifecycle pass their contract and concurrency gates.
